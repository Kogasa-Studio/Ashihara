# 文档编纂规则 v1.0

**适用场景**：Ashihara Mod 技术文档编写  
**创建日期**：2026-04-18  
**面向对象**：AI Agent（主要读者）+ 用户校对  

## 核心原则

### 1. 效率优先
- 目标：最大化AI处理效率和用户校对效率
- 方法：用清晰的结构替代过度修饰，用表格替代散文
- 结果：快速理解和迭代

### 2. 最小化冗余
- 避免重复的内容说明
- 使用相互链接替代复制粘贴
- 长文档时采用"大纲+详解"分离模式

### 3. 明确的目的性
- 每个文档必须有明确的用途
- 不同类型文档遵循不同的模板
- 避免"万能文档"

## 文档类型与模板

### 类型1：系统架构文档

**用途**：解释完整系统的设计和各部件关系  
**目标读者**：AI（实现）+ 用户（审查）

**模板**：
```markdown
# [系统名] 架构设计

> 标签：[分类]
> 状态：[设计阶段]
> 优先级：[重要性]

## 简述
一句话说明系统的职责和核心价值

## 核心模块

### 模块1：[名称]
**职责**：[具体做什么]
**输入**：[接收什么]
**输出**：[产生什么]

代码示例（如果复杂）

关键要点列表（不超过5点）

### 模块2：...

## 集成示例
展示各模块如何协作的完整流程图或代码

## 文件结构规划
目标代码文件的组织方式
```

## 文件夹组织规则

### 何时创建子文件夹

**触发条件**：当某个需求/系统的文档满足以下任一条件时
- 相关文档超过 3 个
- 包含多个独立的实现规范
- 预期会持续增长和扩展

**命名规范**：
```
[系统名]-framework/
├── README.md              (导航和概述)
├── [系统]-design.md       (架构设计)
├── [系统]-implement.md    (实现规范)
├── [系统]-quickref.md     (快速参考)
├── decisions/             (技术决策汇集)
│   ├── decision-001.md
│   ├── decision-002.md
│   └── ...
└── examples/              (代码示例汇集)
    ├── basic-example.java
    ├── advanced-example.java
    └── ...
```

**例外**：
- 少于3个文档的内容保留在父目录
- 单个独立的决策可直接放在主目录

### 更新现有结构时的操作

1. **创建文件夹**
2. **创建README.md**：导航所有子文档和说明
3. **移动或链接相关文档**
4. **更新父目录的索引**

## 文档内容规范

### 格式要求

1. **标题层级**
   - H1 (# ) 仅用于文档标题
   - H2 (## ) 用于主要章节
   - H3 (### ) 用于子章节
   - H4 (#### ) 用于代码块标题

2. **代码块**
   - 所有代码块必须指定语言：\`\`\`java、\`\`\`markdown 等
   - 长代码块 (>30行) 可分段展示，用注释标示关键部分

3. **表格**
   - 用表格替代列表（当项目 ≥ 3 个时）
   - 表格列数限制：最多 5 列（超过则分表或改格式）

4. **链接**
   - 相互链接不同文档
   - 格式：`[文档名](./相对路径.md)`
   - 同系统内链接使用相对路径，跨系统使用绝对路径（从Arch开始）

### 语言风格

1. **面向AI的清晰表达**
   - 避免修辞和拟人化
   - 用"系统做X"替代"我们如何做X"
   - 用"必须"、"应该"、"可以"而非"最好"、"通常"

2. **面向用户校对的友好性**
   - 使用行业标准术语
   - 配图表说明复杂概念
   - 每个关键概念只定义一次，之后用链接指向

3. **emoji使用**
   - **限制使用**：仅在以下情况使用
     - 状态标记：📋(设计) ✅(完成) 🔨(进行中)
     - 导航助手：▶️ ◀️ 等
   - **禁止**：修饰性emoji、表情emoji

### 必填字段

每个文档顶部必须包含元信息块：
```markdown
> 标签：[分类1、分类2]
> 状态：[阶段状态]
> 相关文档：[链接]
> 最后更新：[日期]
```

## 维护规则

### 文档更新时
1. 更新"最后更新"时间戳
2. 如有大幅改动，在README中记录变更日志
3. 同步所有相互链接

### 新建文档时
1. 选择正确的类型模板
2. 从正确的父文档链接指向它
3. 如果是系列文档，更新README导航

### 文档重构时（重要）

**规则**：当对一组相关文档进行重构和优化后，必须清理旧文档

**执行步骤**：
1. 新系统开发完成，所有链接已验证
2. 确认旧文档的内容已完全迁移到新系统
3. 删除被替代的旧文档（见下方"旧文档处理"）
4. 更新父文档的导航和README
5. 记录本次重构的变更日志

**旧文档处理**：
- 如果新文档完全替代旧文档：删除旧文档
- 如果新文档是旧文档的精简版，旧文档作为参考：保留旧文档但在新文档中明确标注
- 如果有版本关系（如v1.0 vs v2.0）：保留旧版本作为历史，新版本标注为当前版本

**示例**（3D UI框架重构）：
- 旧的 `3d-ui-documentation-index.md` → 新的 `3d-ui-framework/README.md`（删除旧版）
- 旧的 `3d-ui-quick-reference.md` → 新的 `3d-ui-framework/3d-ui-quickref.md`（删除旧版）
- 旧的 `3d-ui-implementation-roadmap.md` → 新的 `3d-ui-framework/roadmap.md`（删除旧版）
- 旧的 `3d-ui-system.md` → 新的 `3d-ui-framework/3d-ui-design.md`（保留旧版作为完整参考）
- 旧的 `3d-ui-technical-decisions.md` → 新的 `3d-ui-framework/decisions/INDEX.md`（保留旧版作为完整参考）

### 文档过期时
1. 在顶部添加过期警告
2. 链接到最新版本
3. 保留作为历史记录（除非根据上述重构规则删除）

## 特殊约定

### 代码示例
- 优先提供完整的、可复制运行的代码
- 如果需要简化，用 `// ...` 表示省略部分
- 标注代码示例的完整度：`// 完整示例` vs `// 代码片段`

### 性能数据
- 总是附带测试条件（硬件配置、测试场景）
- 使用"相对性能"（如"快3倍"）时必须说明基准

### 不确定内容
- 使用 `[待确认]` 标记
- 附带澄清或实验计划

## 快速检查清单

新建或更新文档时：

- [ ] 文档有明确的用途和目标读者
- [ ] 使用了合适的文档类型模板
- [ ] 包含完整的元信息块
- [ ] 无冗余和重复内容
- [ ] 代码示例完整且可用
- [ ] 所有链接都能正常工作
- [ ] 表格/图表清晰易懂
- [ ] emoji 使用最小化
- [ ] 术语定义一致
