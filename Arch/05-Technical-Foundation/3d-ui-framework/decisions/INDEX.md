## 核心决策摘要

### 001：Screen继承架构

**选择**：继承Screen  
**理由**：完全兼容，能复用原版基础设施  
**权衡**：需处理2D特定方法

### 002：组件树架构

**选择**：树形组件系统  
**理由**：高度可复用，支持嵌套，事件分发清晰  
**权衡**：增加初期设计成本

### 003：碰撞检测算法

**选择**：OBB + SAT分离轴定理  
**理由**：支持旋转和缩放，精度和性能平衡最优  
**权衡**：实现复杂，需充分测试

**快速替代方案**：Day1可先用AABB快速验证，Day2升级为OBB

### 004：GeckoLib集成

**选择**：InternalControlGeoModel + Mixin  
**理由**：支持代码生成动画，灵活高效  
**权衡**：Mixin可能与其他Mod冲突，需版本管理

### 005：数据绑定策略

**选择**：Property<T>响应式模式  
**理由**：UI和业务逻辑自动同步，易于测试  
**权衡**：增加内存占用

### 006：渲染批处理

**选择**：按RenderType和深度排序的批渲染  
**理由**：减少渲染调用，提高帧率  
**权衡**：增加CPU排序成本（通常可接受）

### 007：网络同步方式

**选择**：事件发布模式  
**理由**：解耦，便于扩展，适合mod环境  
**权衡**：需要额外的验证逻辑

### 008：动画驱动方式

**选择**：InternalAnimationBuilder代码生成  
**理由**：与业务逻辑紧密结合，灵活高效  
**权衡**：动画复杂时代码冗长

### 009：内存管理与缓存

**选择**：对象池 + 弱引用缓存  
**理由**：减少GC压力，提高稳定性  
**权衡**：需要手动生命周期管理

### 010：错误处理与日志

**选择**：分级日志 + 自动降级  
**理由**：便于调试，生产环境稳定  
**权衡**：降级可能掩盖真实问题
